# Install

<div className="lede">
uf is a single native binary. It needs a JavaScript host — Node.js, Bun or
Deno — because Vite and your test bodies run there, but it is not installed
through one.
</div>

**What you will be able to do:** install uf from a release, with Nix or from
source, know what the installer verified, and see which JavaScript host uf will
run on.

**What you need first:** macOS or Linux on x86-64 or ARM64, or Windows on
x86-64; and Node.js or Bun, which Vite and your tests run on.

## From a release

Every tagged release publishes binaries for macOS and Linux on x86-64 and
ARM64, plus Windows on x86-64:

<div className="command"><code>curl -fsSL https://setup.uniflowed.dev | sh</code></div>

On Windows:

<div className="command"><code>irm https://setup.uniflowed.dev/install.ps1 | iex</code></div>

The installer picks the binary for your platform, checks it, and puts it in its bin
directory. Add that directory to `PATH` if it is not already there. The POSIX script works under `sh`, `bash` and `zsh`; the Windows script
runs under PowerShell. Read either one before you run it — they are served from
`https://setup.uniflowed.dev/install.sh` and
`https://setup.uniflowed.dev/install.ps1` if you would rather fetch them first.

### What it checks, and what that proves

Two separate things, because they answer two questions.

The **SHA-256** beside the archive proves *transit*: the bytes that arrived are
the bytes that host advertised, which catches a truncated download or a
corrupting proxy. It proves nothing about origin — the archive and the checksum
come from the same host, so whoever can replace one can replace the other.

The **signature** proves *origin*. Every release archive is signed with keyless
Sigstore from the release workflow's own GitHub OIDC identity, and the installer
verifies the bundle against that identity — a root that is not on the host
serving the archive. Install [`cosign`](https://github.com/sigstore/cosign) and
the check runs; without it the installer says the signature was not checked
rather than implying it was.

| Variable | Default | What it does |
| --- | --- | --- |
| `UF_VERIFY_ORIGIN` | `auto` | `require` refuses an install whose origin nothing established; `off` skips the check |
| `UF_CHECKSUM_BASE` | unset | A `<base>/<version>/<asset>.sha256` layout on a host that does **not** serve the archive. The two digests must agree |
| `UF_VERSION` | `latest` | A specific release |
| `UF_RELEASE_BASE` | unset | A mirror serving the flat `<base>/<version>/<asset>` layout |
| `UF_INSTALL_ROOT`, `UF_BIN_DIR` | XDG paths | Where the runtime and the shims go |

A signature that is present and does not verify **always** refuses, whatever
`UF_VERIFY_ORIGIN` says — and so does a second opinion that disagrees. The
failure prints cosign's own words, because a signature made by somebody else and
a `cosign` too old to read the bundle exit the same way and are not the same
problem. uf's own release pipeline installs with `UF_VERIFY_ORIGIN=require`, so
a release whose signature does not verify never reaches you.

The default is `auto` and not `require` for one reason, which will stop being
true: releases published before signing existed carry no bundle, and a default
that refused them would make every pinned `UF_VERSION` of an older release
uninstallable by the current script. Pass `UF_VERIFY_ORIGIN=require` today to
get the stricter behaviour; it is what the default becomes once every release a
person can still install is signed.

### On Windows

The PowerShell installer installs `uf.exe`, `ufr.exe` and `ufx.exe` into
`%USERPROFILE%\.local\bin` by default. Add that directory to `PATH` if your
current terminal cannot find `uf` afterwards. `UF_INSTALL_ROOT`, `UF_BIN_DIR`,
`UF_VERSION` and `UF_RELEASE_BASE` work the same way as they do for the POSIX
script.

WSL2 still works too, and uses the Linux install line above.

### Updating, and going back

<div className="command"><code>uf self-update</code></div>

installs the newest release through the same script, with the same checks, and
switches `uf`, `ufr` and `ufx` to it. `uf self-update --check` says whether
there is a newer release without installing it, and
`uf self-update 0.0.0-alpha.35` installs that release instead of the newest.

The version an update replaces stays in the store, under
`~/.local/share/uf/runtimes`, and is recorded beside it, so

<div className="command"><code>uf self-update --rollback</code></div>

switches back to it without the network. Running the installer again records
what it replaced in the same place, so a rollback after `curl … | sh` returns
to the version that one replaced.

Every switch, the installer's and uf's, renames each link over the old one with
`uf` last, and only ever renames a whole runtime into the store. An update that
is interrupted leaves the old version working, or the new one — never a `uf`
that points at nothing.

### Uninstalling

<div className="command"><code>uf self-uninstall</code></div>

lists the links, the runtimes and the toolchain store it would remove, asks, and
removes them. `uf self-uninstall --dry-run` only lists them. A `uf` it did not
link, your projects and your shell profile are left as they are — the installer
never edits a profile, so there is no line of uf's to take back out.

## With Nix

The repository is a flake, and it is the whole install: it pins the Rust
toolchain, fetches Meta's Flow port at the commit uf was built against, and
applies uf's patches to it, so a build here is the same build everywhere.

Run it without installing anything:

<div className="command"><code>nix run github:ubugeeei-prod/uf</code></div>

Install it into a profile:

<div className="command"><code>nix profile install github:ubugeeei-prod/uf</code></div>

Both give you `uf`, `ufr` and `ufx`. `nix run github:ubugeeei-prod/uf#ufx` runs
one of the others directly.

### In a system configuration

For NixOS and nix-darwin, `nixosModules.default` and `darwinModules.default`
take the same option; home-manager takes `homeManagerModules.default`:

```nix
{
  inputs.uf.url = "github:ubugeeei-prod/uf";

  # NixOS or nix-darwin
  imports = [ inputs.uf.nixosModules.default ];
  programs.uf.enable = true;
}
```

Or take the overlay, if you would rather have `pkgs.uf` and place it yourself.
It composes in the Rust overlay uf needs, so this is the only line required:

```nix
{
  nixpkgs.overlays = [ inputs.uf.overlays.default ];
  environment.systemPackages = [ pkgs.uf ];
}
```

There is no binary cache for these yet, so the first build compiles the Flow
parser and the React Compiler from source and takes a while. The release
tarballs above are the fast path; this is the reproducible one.

`aarch64-darwin`, `aarch64-linux`, `x86_64-darwin` and `x86_64-linux` are all
declared. CI builds `x86_64-linux` on every change to the flake and weekly on a
schedule; the other three are evaluated on every change but not built, so a
break specific to one of them would reach you before it reached CI.

## From source

Without Nix. uf builds with a pinned nightly Rust toolchain — Flow's own crates
need `box_patterns`, which is still unstable — and vendors the Flow and React
Compiler sources as submodules.

<div className="command"><code>git clone --recurse-submodules https://github.com/ubugeeei-prod/uf</code></div>
<div className="command"><code>cd uf && cargo build --release --bin uf</code></div>

The toolchain file in the repository selects the right nightly, so `rustup` will
fetch it on the first build. Expect the first build to take a while: it compiles
the Flow parser and the React Compiler.

## The JavaScript host

uf does the parsing, transforming, scheduling and reporting itself, and hands
the rest to a host:

| Host | Dev and build | Tests | Notes |
| --- | --- | --- | --- |
| Node.js | yes | yes | The default. Flow modules load through `module.registerHooks()`, or `module.register()` on a Node older than 22.15. |
| Bun | yes | yes | Flow modules load through a `--preload` plugin. |
| Deno | yes, from 2.8 | yes, from 2.8 | Flow modules load through `node:module`'s `registerHooks`, which Deno implemented in 2.8; an older Deno is refused by version. `uf test --coverage` is Node's, and a test that imports a package with a native addon fails on Deno, which is Deno's to fix. See [#246](https://github.com/ubugeeei-prod/uf/issues/246). |

uf detects what is available and picks one. To pin a project to a host:

<div className="command"><code>uf use bun</code></div>

which writes the choice into `uf.config.js`. `uf info` prints what was detected
and what was chosen.

## Checking the install

<div className="command"><code>uf info</code></div>

prints the version, the resolved host, and the project it found. If it reports
no project, you are outside one — that is fine, and [the next
page](/guide/project) starts one.

# Editors

<div className="lede">
`uf lsp` is uf's language server, and every integration under
[`editors/`](https://github.com/ubugeeei-prod/uf/tree/main/editors) is a client of
it. What an editor shows — a lint finding under a line, a file formatted on save,
a quick fix — comes from the same crates `uf lint` and `uf fmt` run in a terminal,
so the editor and CI cannot disagree about a file.
</div>

**What you will be able to do:** set up your editor, know exactly what the server
answers and what it does not, and make sure it formats and lints to your project's
configuration rather than to uf's defaults.

**What you need first:** uf [installed](/guide/install), and a project with a
`uf.config.js` — [Your first project](/guide/project) makes one.

## Your editor

Every editor on this list that ships a JavaScript language server, or usually
runs one, reads a Flow file as TypeScript: `component`, `hook`, `match`,
`renders` and every type annotation are reported as errors beside uf's. Each
page below turns that off **for a uf project only**, in a file you commit with
the project, so the same editor still checks a TypeScript project as before.
Each page also says what the editor keeps doing that no setting turns off.

| Editor | Its JavaScript server | Turned off, per project, by | uf formats on save | Left on | CI runs the integration |
| --- | --- | --- | --- | --- | --- |
| [VS Code and Cursor](/guide/editors/vscode) | TypeScript's, built in | `.vscode/settings.json`: `javascript.validate.enable` and `js/ts.validate.enabled`, which the extension writes | `editor.defaultFormatter` | the built-in hover, definitions and suggestions, unless the built-in extension is disabled for the workspace | its decisions, and its wiring against a stand-in for VS Code |
| [Zed](/guide/editors/zed) | vtsls | `.zed/settings.json`: `"!vtsls"` in `language_servers` | `formatter` and `format_on_save` | Zed's tree-sitter highlighting, which does not know Flow's component syntax | its decisions, on the host |
| [JetBrains IDEs](/guide/editors/jetbrains) | the IDE's own JavaScript and TypeScript support | the Flow language level and the TypeScript service setting | Reformat Code, through LSP4IJ | the IDE's own parser and inspections (not verified against Flow's component syntax) | no |
| [Neovim and Vim](/guide/editors/neovim) | usually `ts_ls` or `vtsls`, from nvim-lspconfig | `uf.lua`'s `exclude`, or a `root_dir` that skips uf projects | `format_on_save` | nothing in Neovim; in Vim, a vim-lsp TypeScript server you disable yourself | Neovim, headless |
| [Helix](/guide/editors/helix) | typescript-language-server | `.helix/languages.toml`: `language-servers = ["uf"]` | `auto-format` | nothing | no |
| [Emacs](/guide/editors/emacs) | typescript-language-server, from Eglot or lsp-mode | `uf.el`, which serves uf projects with uf and everything else as before | `uf-format-on-save` | nothing | batch Emacs |

From a terminal, `uf editor install <editor>` installs the integration, and
`uf editor setup <editor>` writes the project's file from the table. Setup adds
what is missing, keeps anything the project already sets, and with `--check`
writes nothing and fails when something is missing.

Every one of them gets uf's diagnostics, hover, go to definition, go to type
definition, completion, quick fixes, fix-all and formatting, because they all
come from `uf lsp`. None of them gets rename or references, because `uf lsp`
does not serve those.

## What the server answers

A session with one file, `app/flags.js`, which declares `export type Flag = bool;`:

<figure className="terminal">

```
initialize
{"serverInfo":{"name":"uf-lsp","version":"…"},"capabilities":{"textDocumentSync":1,"documentFormattingProvider":true,"hoverProvider":true,"codeActionProvider":{"codeActionKinds":["quickfix","source.fixAll.uf"]},"completionProvider":{"triggerCharacters":["\"","@","."]},"definitionProvider":true,"typeDefinitionProvider":true}}

textDocument/publishDiagnostics
flow/deprecated-type  severity 1  4:20  the `bool` type alias is deprecated; write `boolean`

textDocument/codeAction
quickfix          Replace `bool` with `boolean`  (preferred)
source.fixAll.uf  Fix all uf lint problems in this file

textDocument/hover on `bool`
**`flow/deprecated-type`** · error

the `bool` type alias is deprecated; write `boolean`

---

Flow's own lint set · default `error` · decided from the source text
```

</figure>

| | What it is | Where it comes from |
| --- | --- | --- |
| **Diagnostics** | Pushed when a document opens and on every change, cleared when it closes. The source is `uf` and the code is the rule id | `uf_lint` — the rules `uf lint` runs, at the levels your `uf.config.js` sets |
| **Type errors** | Pushed beside the lint diagnostics once typing pauses for 150 ms, for the edited file first and then every other open file, since any of them may import it. The source is `flow`, the code is Flow's error code (`incompatible-type`), and each location the message refers to is `relatedInformation`, labelled `[1] string`, `[2] number` as `uf check` numbers them. None while the file does not parse: the syntax error is the linter's | the checker [`uf check`](/guide/check) runs, over the same modules and suppression comments, so the editor and the terminal report the same errors |
| **Formatting** | One edit over the whole document | `uf_fmt`, the printer `uf fmt` uses, with your `fmt` options — not the editor's tab settings |
| **Quick fixes** | `quickfix` actions for a diagnostic with a mechanical answer, and a "format this document" action where formatting clears a whitespace finding | the fix catalogue `uf lint --fix` uses |
| **Fix all** | `source.fixAll.uf`: every **safe** fix in the file at once | the same catalogue; the unsafe tier is a quick fix you pick, never part of fix-all |
| **Hover** | The rule behind a diagnostic, what an import specifier names, what a rule id in a suppression comment means, and a key of `uf.config.js`; anywhere else in a Flow file, the inferred type under the cursor, printed as Flow | the lint rules, uf's module registry, `@uniflowed/config`, and Flow's own inference |
| **Go to definition** | Where the name under the cursor is declared: in the same file, in the file it was imported from, in a package under `node_modules`, or in the project's `flow-typed/` library definitions | Flow's inference |
| **Go to type definition** | Where the named types in the type under the cursor are declared: for `const user: User`, the `type User` | Flow's inference |
| **Completion** | In `uf.config.js`: the keys valid at the cursor, with their documentation and type; the values of a key whose type is a fixed set; and in a tool spec like `runtime: "node@26"`, the names its key takes and, after `@`, that tool's versions, newest first. In any other Flow file: after `value.`, the members of `value`'s type with their types, and elsewhere the names in scope | `@uniflowed/config`'s Flow type, compiled into `uf`, so it works in a file that is half-typed; versions from the release lists uf caches under `$XDG_CACHE_HOME/uf/index`, fetched in the background and never on a request's time. Elsewhere, Flow's own completion service |

The type answers come from the checker [`uf check`](/guide/check) runs, over the
same modules: the server reads the whole project the way `uf check` with no
paths does — every source, what those import, the packages under
`node_modules` they reach, and `flow-typed/` — and keeps it in memory. With
`app/main.js` importing that file:

<figure className="terminal">

```
app/main.js
// @flow
import { flags } from "./flags.js";
const first = flags[0];

textDocument/hover on `first`
const first: Flag

textDocument/definition on `flags`
app/flags.js  3:14

textDocument/typeDefinition on `first`
app/flags.js  2:13

textDocument/completion after `first.`
toString  () => string
valueOf   () => boolean
```

</figure>

It reads the project when the editor says `initialized`, in the background, so
the first question may wait for that to finish; after it, a hover is answered
from memory. An edit re-infers the edited file when it is next asked about, and
the files that import it when *they* are — not the project. What the editor has
open and unsaved is what is asked about, not the file on disk.

A file that does not parse — half a keystroke into an edit — has no inference
to ask, so hover and definitions answer nothing until it parses again.
Completion does answer there: `value.` is the one place a file is most often
broken, and the completion service reads it as an access being typed.

What it does not answer: rename, find-references, document symbols and
signature help. It advertises none of them, and a request for one is refused
rather than left waiting:

<figure className="terminal">

```
textDocument/references
{"code":-32601,"message":"uf lsp does not serve `textDocument/references`"}
```

</figure>

## Which configuration it reads

The server reads the project's configuration **once, when it starts**: from the
directory `--cwd` names, or its working directory, walking up to the nearest
`uf.config.js`, `package.json` or `.git`. Three consequences:

- **Editing `uf.config.js` needs a restart.** The server has no way to be told.
  The VS Code extension watches the file and restarts by itself; every other
  editor's page says how to restart it.
- **A configuration it cannot read is not reported.** The server falls back to
  uf's defaults, and the editor formats and lints to those without a word. The
  check is to format a file in the editor and run `uf fmt --check` in a terminal:
  if they disagree, the server is reading something else.
- **The walk stops at the first `package.json`.** In a workspace, a member with
  its own `package.json` and no `uf.config.js` gets uf's defaults, not the root's
  configuration.

Every integration either starts the server in the project folder or names it
with `uf lsp --cwd <dir>`; the two say the same thing.

The project's `ignore` list does not reach the server either: a file you have
opened is linted, even one `uf lint` would skip.

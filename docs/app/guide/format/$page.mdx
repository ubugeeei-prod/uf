# Formatting and linting

<div className="lede">
Both read the same tree the compiler does. The formatter is a Rust printer over
Meta's Flow parser; the linter runs uf's own rules alongside Flow's built-in
ones, in one pass, with one report.
</div>

**What you will be able to do:** format a project the way Prettier would, lint
it with uf's rules and Flow's in one pass, apply the fixes, and put both in CI.

**What you need first:** a project — [Your first project](/guide/project).

## uf fmt

<div className="command"><code>uf fmt</code></div>

Formats every Flow, JavaScript, JSON, CSS and TypeScript file in the project —
Markdown is not among them. `--check` exits non-zero instead of writing, which
is what CI should run.

Flow files go through the official Flow parser and a printer written for it, so
`component`, `hook`, `renders`, `match` and enums are formatted as first-class
syntax rather than survived. The output follows Prettier's conventions — double quotes, trailing commas,
the same line-breaking decisions — because the point of a formatter is that
nobody argues about it, and Prettier already won that argument. The default
width is 100 rather than Prettier's 80; `fmt.lineWidth` changes it.

That claim is checked rather than asserted: every fixture in `uf_fmt`'s suite
is compared byte for byte against Prettier's own output for the same input.

### GraphQL in a tagged template

`uf fmt` formats the GraphQL inside a template tagged `graphql`, `gql` or
`graphql.experimental`, a template passed to `graphql(…)`, and one written
behind a `/* GraphQL */` comment — and re-indents it to the code around it,
which is the part you notice:

```js
const fragment = graphql`
        fragment UserFragment on User {
          username
        }
      `;
```

becomes

```js
const fragment = graphql`
  fragment UserFragment on User {
    username
  }
`;
```

A template with `${…}` in it works when each run of text between the holes is
a complete document on its own — a trailing `${Fragment}` is the usual case —
and is left alone when it is not. That is Prettier's rule, not uf's.

**A template uf will not reprint, it does not touch.** It comes back exactly
as you wrote it rather than approximately right, and there are four reasons
for that to happen: the document holds a `#` comment, it holds a string with
a control character in it, it is not GraphQL, or it nests more than 128 deep.
The comment case is the one you are likely to meet — uf does not yet
reproduce where Prettier puts a GraphQL comment, and moving a comment to the
wrong line is worse than leaving the query alone.

GraphQL is the only embedded language uf reads. `css`, `html`, `sql` and
`markdown` templates go out exactly as written, where Prettier would format
them.

Files uf has no opinion about — JSON, CSS, TypeScript — are handed to Biome,
which is also Rust and also fast. uf runs the binary your project has rather
than shipping one, so Biome is a formatter you install; `fmt.nonFlow.formatter`
names a different one, or `"none"`.

When it is not installed, `uf fmt` says so and names the files it left alone,
and that is a warning rather than a failure: uf picked Biome, you did not, and
the exit code answers for the files uf can format itself. Write
`fmt.nonFlow.formatter` in `uf.config.js` and the answer changes — a formatter
you asked for by name and do not have fails the run, which is what a CI job
that checks the JSON as well wants.

Measured on a 133 kB Flow and JSX file:

| | Time | Throughput |
| --- | --- | --- |
| Parse alone | 10.4 ms | 12.9 MiB/s |
| Parse and format | 17.9 ms | 7.4 MiB/s |
| `--check`, already formatted | 18.0 ms | 7.5 MiB/s |

The parser is 58% of that. The target is 10 MB/s end to end, and the printer is
not what is standing between here and there.

### When format is the slow check

Start with the files, not the formatter. `uf fmt` walks the same project set as
`uf lint`, `uf check`, `uf test` and `uf doc`: `.gitignore`, `.ignore`,
`.uf`/`.git`, then the top-level `ignore` list in `uf.config.js`. A generated
directory in none of those lists is source, so it will be printed.

```sh
uf fmt --check packages/ui
uf fmt --check dialog.js
```

The path arguments are substring filters. They do not use a glob language, and
they do not silently pass when nothing matched; a filter that reads zero files
is an error. That makes a slow full-project run easy to cut down without
creating a second configuration file.

The next thing to check is who is formatting the file. Flow files are always
printed by uf. JSON, CSS and TypeScript are delegated to
`fmt.nonFlow.formatter`, Biome by default:

```sh
uf explain fmt --json
```

If a slow run is all Flow, the cost is parse plus print. If it is all JSON or
CSS, the cost belongs to the provider uf started. If it is Markdown, it should
not be in the run at all — uf does not format Markdown.

## uf lint

<div className="command"><code>uf lint</code></div>

Runs uf's rules and Flow's own lints together and prints one list. `--json`
emits the report machine-readably.

Flow's built-in lints — `sketchy-null`, `unclear-type`, `deprecated-type`,
`unnecessary-optional-chain` and the rest — are configured in `uf.config.js`
alongside uf's rules rather than in a separate `.flowconfig` section, because a
project should have one place where "this is an error here" is written down.

### Which rules there are

<div className="command"><code>uf lint --rules</code></div>

Lists every rule instead of linting: the level it runs at in this project, the
command that fixes its findings, and what it checks. The level is read from
`uf.config.js` over the defaults, so the list answers "is this rule on for us"
rather than "is it on by default", and `--json` prints the same list for a
script. Read it rather than a list on this page — a rule name or a count written
into a guide goes stale the day a rule is added, and the command cannot.

### What a lint run tells you

`uf lint --json` is the report to feed an editor, CI annotation step, or a
small script:

```json
{
  "command": "uf lint",
  "filesChecked": 1,
  "errors": 0,
  "warnings": 0,
  "diagnostics": [],
  "unavailableRules": []
}
```

`diagnostics` is the list that should become annotations. `errors` and
`warnings` are the totals a CI step should branch on. `filesChecked` is a guard
against a path filter that was too narrow, and `unavailableRules` is part of the
contract: a rule that needs inference and could not run is named instead of
quietly disappearing.

`uf explain lint --json` answers a different question:

```json
{
  "command": "uf lint",
  "stages": [
    { "name": "uf rules", "provider": "Rust", "detail": "63 rules configured" },
    { "name": "Flow's own lints", "provider": "OfficialFlowRust" }
  ]
}
```

Use the first report when you need findings. Use the second when you need to
know whose work is in the run before chasing performance. The important part is
that both are command output rather than documentation promises: if a rule is
added, disabled or made unavailable, the machine-readable answer changes with
the command.

### Fixing what it finds

<div className="command"><code>uf lint --fix</code></div>

Applies every fix uf is willing to make without asking, writes the files, and
reports how many it applied and what it left. It is the same catalogue the
language server offers in an editor, reached from a terminal, a git hook or CI
rather than only from a lightbulb menu.

Two tiers, and the difference is real. `--fix` applies only the fixes where the
program afterwards means what it meant before — `bool` becomes `boolean`, and
nothing has been decided on your behalf. `--fix-unsafe` also applies the ones
whose correctness rests on something the rule could not check: `export let
count = 0` becomes `export const count = 0`, which still parses and still
formats, and throws at run time if anything reassigns the binding. Read that
diff before you commit it.

Most rules have no fix at all, which is deliberate — `uf lint --rules` names the
few that do, and the flag that applies each. `flow/unclear-type`
could turn `any` into `mixed`, an opaque type, or a generated router type
depending on what you meant; three answers is none, and guessing at one is
worse than leaving the finding where you can see it.

What is written parses, and running it twice is running it once. Every file
that passed `uf fmt --check` before the fix passes it after: a file the
formatter was content with is reprinted around the edit, because four bytes is
enough to push a line past the print width. A file that was already failing
that check keeps failing it — the edit is written as the edit left it, and
laying out a file nobody asked to have laid out is `uf fmt`'s job rather than
this one's. The [CLI reference](/reference/cli) spells out each of those and
what the exit status means.

`uf fmt`, `uf lint` and `uf check` all take paths, the way `uf test` does:

<div className="command"><code>uf lint packages/ui</code></div>

Anything whose path contains one of the arguments is read and nothing else, so
`uf fmt dialog.js` is a way to format the file in front of you. A pattern that
matches nothing is an error rather than a clean run.

### Project rules

A rule your team writes is a JavaScript module listed in `plugins` and switched
on in `lint.rules`. `uf lint` runs it beside uf's own rules, into one report:

```js
// uf.config.js
export default {
  plugins: ["./rules/acme.js"],
  lint: { rules: { "acme/no-foo": "error" } },
};
```

```js
// rules/acme.js
export default {
  name: "acme",
  rules: {
    "no-foo": {
      meta: { messages: { reserved: "`{{ name }}` is reserved for the build" } },
      create(context) {
        return {
          Identifier(node) {
            if (node.name === "foo") {
              context.report({ node, messageId: "reserved", data: { name: node.name } });
            }
          },
        };
      },
    },
  },
};
```

The shape is ESLint's, so a rule you already have mostly moves as it is. A
plugin is a module whose default export has a `name` and `rules`, and a rule's
id is the two joined: `acme/no-foo`. Vite ignores a key it does not know, so
the same object can also be one of the project's Vite plugins. What a rule
gets:

- **Listeners** keyed by ESTree node type, and by the type with `:exit` on the
  way out. The tree is the one uf's own Flow parser produced, so type
  annotations and component syntax are nodes like any other, and every node
  has a `parent`. There are no selectors beyond a node type. An identifier
  with a type annotation spans the annotation too, as in any Flow ESTree, so a
  fix that renames one replaces `node.name.length` characters from
  `node.range[0]` rather than the whole node.
- **`context.report`** with a `node` or a `loc` (lines from 1, columns from 0),
  and a `message`, or a `messageId` from `meta.messages` filled from `data`.
- **`context.sourceCode`** — `text`, `ast`, `lines`, `getText(node)`,
  `getLocFromIndex` and `getIndexFromLoc` — with `context.filename` and
  `context.cwd`.
- **`fix`**, reported only by a rule that sets `meta.fixable`, with ESLint's
  fixer: `replaceText`, `replaceTextRange`, `insertTextBefore`,
  `insertTextAfter`, their `Range` forms, `remove` and `removeRange`.

What is not there fails out loud instead of answering nothing. There is no
scope analysis, no token list, and no `context.options`, because `lint.rules`
takes a level and nothing else. A rule that calls `getScope` throws, and a rule
that throws is named in the report.

The rules run in one worker on the project's Capability JS Host — Node.js or
Bun, through the Flow loader `uf test` uses, so a rule module can be written in
Flow — and the worker is started only when a project rule is on, from
`@uniflowed/host`, which has to be installed. Its cost is bounded and reported.
It has 30 seconds to load the plugins and 5 seconds for each file; a worker past
either is stopped and the file named, and after three workers the remaining
files are named rather than tried. `uf lint --json` carries a `projectRules`
object with the time spent inside each rule, the wall time of the whole pass
and every problem — a plugin that did not import, a rule no plugin defines, a
file that ran out of time — and any problem fails the run.

A rule's fixes go through the same two tiers as uf's own, and the rule picks
the tier with the word ESLint already gives it. `meta.fixable: "whitespace"`
promises edits that only move layout, and `--fix` applies those; `"code"` is
applied by `--fix-unsafe` alone, because uf cannot read an edit to find out
whether the program still means what it meant. Either way the result has to
parse and stay formatted, exactly as with uf's own fixes.

The language server runs project rules too, with one worker for the whole
editor session. Their findings appear beside uf's, a finding with a fix has it
in the lightbulb menu, "Fix all" on save applies the `"whitespace"` ones, and
anything that keeps a rule from answering is written to the editor's log for
the server.

### When lint is too expensive

The slowest lint is usually not "the linter"; it is one rule repeatedly asking
for a shape that should have been computed once. That is the class of bug behind
[#668](https://github.com/ubugeeei-prod/uf/issues/668): one rule spent most of
the allocation budget building a Babel AST for a file that uf had already
parsed.

The public workflow is:

1. Narrow the path until the cost follows a directory or a single large file.
2. Run `uf lint --json <path>` and confirm `filesChecked` is the number you
   meant.
3. Run `uf explain lint --json` to record which lint stages were in the run.
4. File the slow case with the file size, the rule name if one dominates the
   findings, and the command output.

There is no `uf profile` subcommand. The repository has profiler support for
its own benches and allocation reports, but a project run should not depend on
an internal profiling interface. Until a public profiler exists, the stable
answers are the narrowed command, the JSON report and the explain output.

### Coming from ESLint

Where each rule of the four ESLint plugins React projects most often run lands
in uf. A rule id on the right is the uf rule that answers the same question, and
`uf lint --rules` shows its level in your project and whether it has a fix. The
other answers:

- **Flow** — `uf check`'s type inference reports it, so no lint rule has to
  guess.
- **`uf fmt`** — layout, which is the formatter's to decide.
- **React Compiler** — uf compiles components with it, and it memoizes what the
  rule would have you hoist or wrap.
- **Not needed** — what the rule guards against does not exist in a uf project;
  the row says why.
- **Not planned** — rules for class components, their lifecycle methods and the
  legacy APIs around them. uf's React rules are written for component syntax.
- **Project rule** — a team's convention rather than a defect. uf does not ship
  conventions as defaults; a project's own rules are how a team keeps them
  ([#974](https://github.com/ubugeeei-prod/uf/issues/974)).
- **Not yet** — a defect uf does not catch today, tracked in the linked issue.

"Needs inference" marks a uf rule that waits on Flow type inference, which uf
does not implement yet: a run names it under `unavailableRules` instead of
running it.

## uf check

`uf check` runs this page's linter and then Flow's type inference, so every lint
finding here fails a check as well. The inference half — what an import resolves
to, the library definitions it reads, and a JSON report with two lists of
diagnostics — has a page of its own: [Type checking](/guide/check).

## In CI

<div className="command"><code>uf fmt --check && uf lint && uf check && uf test</code></div>

Four commands, no configuration, and each one exits non-zero when it should. Run
them in that order when you want the cheapest failure first:

| Step | Why it goes there |
| --- | --- |
| `uf fmt --check` | cheapest and writes nothing |
| `uf lint` | catches syntax, framework and policy errors before inference |
| `uf check` | reruns lint, then adds Flow inference |
| `uf test` | runs code, so it pays host start-up and fixture cost |

If CI is split into jobs, keep `fmt` and `lint` separate even though `check`
includes lint. A contributor wants the fast, precise failure when a file only
needs formatting; the release gate still wants `check` as the command that says
the project is typed.

Better still, name them once. `uf.config.js` takes tasks, `uf run ci` runs
them, and the pipeline calls the same thing:

```js
export default defineConfig({
  tasks: {
    "fmt:check": "uf fmt --check",
    lint: "uf lint",
    check: "uf check",
    test: "uf test",
    ci: { command: "echo ok", dependsOn: ["fmt:check", "lint", "check", "test"] },
  },
});
```

A check that is in the pipeline and not in `uf.config.js` is a check a
contributor cannot run before pushing. uf's own repository is set up this way —
its CI builds `uf` once and every job runs `uf run <task>`.

# Agents

<div className="lede">
`uf mcp` serves the Model Context Protocol over stdio, so a coding agent can run
the checks a person runs — lint, type check, tests, the route table — and read
the same JSON reports CI reads, rather than scraping a terminal. Eight tools, and
two of them write.
</div>

**What you will be able to do:** register uf with an MCP client, tell which tools
read and which write, read what a call returns, and know where the server's
limits are before an agent leans on them.

**What you need first:** a uf project — [Start](/guide/start) makes one — and a
client that starts stdio MCP servers. Claude Code is the example below; any
client that takes a command and its arguments works the same way.

## Registering it

`uf mcp` is started by the client and talks JSON-RPC over its stdin and stdout,
one message per line. It is not a daemon and has no port. Typed into a terminal,
where there is no client on the other end, it says so and exits:

<figure className="terminal">

```
uf mcp: Model Context Protocol stdio server ready
```

</figure>

The project is decided once, when the server starts: the directory it was
started in, or the one `--cwd` names, walked up to the nearest `uf.config.js`,
`package.json` or `.git`. Nothing a client sends afterwards changes it. So for a
client you run from anywhere, name the project:

```sh
claude mcp add uf -- uf --cwd /path/to/project mcp
```

Everything after `--` is handed to the command untouched
([Claude Code's MCP documentation](https://code.claude.com/docs/en/mcp)). A
project-scoped `.mcp.json` is committed and shared, so it cannot carry your
absolute path; written without one, it runs `uf mcp` in whatever directory the
client starts servers in, and uf walks up from there:

```json
{
  "mcpServers": {
    "uf": { "command": "uf", "args": ["mcp"] }
  }
}
```

If the answers look like they are about the wrong directory, call `uf_info`: it
prints the working directory the server was given.

## The tools

`tools/list` names eight, and each description ends with one sentence saying
what the tool does to your checkout. Every tool runs the command it is named
after, in the server's own process, with the arguments below:

| Tool | Runs | Arguments | Its description ends |
| --- | --- | --- | --- |
| `uf_check` | `uf check --json` | `paths` | Changes none of your files, … |
| `uf_lint` | `uf lint --json` | `paths` | Changes none of your files, … |
| `uf_info` | `uf info` | — | Changes none of your files, … |
| `uf_routes` | `uf routes list` | — | Changes none of your files, … |
| `uf_explain` | `uf explain <command> --json` | `command`, required | Changes none of your files, … |
| `uf_test` | `uf test --json` | `filter`, `paths` | RUNS the project's own code. |
| `uf_fmt_write` | `uf fmt` | `paths` | WRITES to files in the checkout. |
| `uf_lint_fix` | `uf lint --fix --json` | `paths` | WRITES to files in the checkout. |

The first five end "Changes none of your files, though uf may write its own
cache under `.uf/cache/`", and `uf_check`'s description names the one it keeps:
what it inferred, in `.uf/cache/check/`.

`paths` narrows a command to files whose path contains one of the strings, the
way the command line's own `PATH` arguments do. `uf_lint_fix` applies the
[safe fixes](/reference/cli#uf-lint) only; the unsafe tier is not a tool. There
is no tool for `uf build`, `uf dev`, `uf install` or `uf fmt --check`, and the
server offers no resources and no prompts.

## What a call returns

A tool result is a list of text blocks and an `isError` flag. The first block is
what the command printed — JSON for `uf_check`, `uf_lint`, `uf_lint_fix`,
`uf_explain` and `uf_test`, the command's own text for the other three. A command
that fails keeps its report whole in the first block and adds the reason as a
second, so the JSON still parses. From a session with one deliberate type error
in `app/price.js`:

<figure className="terminal">

```
tools/call uf_lint {"paths":["app/"]}
isError: false; blocks: 1
{
  "command": "uf lint",
  "filesChecked": 6,
  "errors": 0,
  "warnings": 0,
  "diagnostics": [],
  …
}

tools/call uf_check {"paths":["app/price.js"]}
isError: true; blocks: 2
errors: 1; typeCheck.status: checked
first type diagnostic: incompatible-type at app/price.js:2:30
second block: "uf check failed with 1 error"
```

</figure>

A failing check is `isError: true` inside an ordinary result, not a protocol
error: the call worked, and its answer is that the project does not check. A tool
that does not exist is answered the same way, and so is a call whose arguments do
not fit the tool's `inputSchema` — a key it does not have, a value of the wrong
type, a missing `command` — which names the argument and runs nothing. Only a
method the server has no answer for at all is a JSON-RPC error:

<figure className="terminal">

```
tools/call uf_build
← {"jsonrpc":"2.0","id":5,"result":{"content":[{"type":"text","text":"no tool named \"uf_build\""}],"isError":true}}
tools/call uf_lint {"pathz":["app/"]}
← {"jsonrpc":"2.0","id":6,"result":{"content":[{"type":"text","text":"uf_lint did not run: `pathz` is not an argument; the arguments are `paths`"}],"isError":true}}
resources/list
← {"jsonrpc":"2.0","id":7,"error":{"code":-32601,"message":"this server has no method \"resources/list\""}}
```

</figure>

[Type checking](/guide/check) has the whole shape of the report `uf_check`
returns, including the one trap in it: `errors` is the sum of the lint findings in
`diagnostics` and the type errors in `typeCheck.diagnostics`.

## What an agent should not assume

These are the limits of the server as it is, and the ones that are defects have
issues:

- **`paths` stays inside the project — over MCP.** An entry that is an absolute
  path, climbs out with `..`, or leads out through a symbolic link is refused,
  naming the entry, before anything is read. On the command line
  `uf fmt ../elsewhere` still does what it says, because the person running it
  typed it. Inside the project there is no confirmation step, allow-list or
  read-only mode, so a client that asks before a tool writes is the only guard.
- **Changing none of your files is not writing nothing.** `uf_check` writes its
  inference cache under `.uf/cache/check/`, and `uf_test` writes
  `.uf/test-timings.json`, beside whatever the tests themselves write.
- **`uf_info` does not describe the project.** It prints uf's version, the
  machine and the working directory, and reads no `uf.config.js`. `uf_explain` is
  the tool that says what a command will do and why.
- **`uf_test` runs your tests with the access your project gives them.** It needs
  the project installed — it stops at `@uniflowed/host` is not installed
  otherwise — and on a host with no `permissions` declared, nothing restricts what
  a test reaches.
- **One call at a time.** The server answers requests in order, so a long
  `uf_test` holds up every call behind it, and `notifications/cancelled` cancels
  nothing.
- **Warnings are not in the result.** What a command or a test worker writes to
  stderr goes to the server's stderr, which the client may or may not show you.
- **One protocol version.** The server answers `2024-11-05` whatever the client
  asked for.

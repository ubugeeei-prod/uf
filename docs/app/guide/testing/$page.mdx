# Testing

<div className="lede">
`uf test` is a Rust runner with JavaScript workers. Rust decides what runs, in
what order, on how many cores, and what the report says; the host runs the
bodies, because running JavaScript is the one thing Rust cannot do.
</div>

**What you will be able to do:** write tests beside the code they test, query
accessibility and React Native trees, replace a module, run and narrow a suite,
use browser mode and coverage, and know where the runner stands against Bun.

**What you need first:** a project with its dependencies installed —
[Dependencies](/guide/dependencies). Without them, a run stops at
`@uniflowed/host`.

## The performance model

The runner is split so the expensive and unstable work is isolated. Rust owns
the project walk, declaration discovery, scheduling, retries, reporters and
coverage thresholds. A JavaScript host owns module evaluation and the test body.
That gives uf a place to keep improving the loop without changing the API a test
imports.

| Phase | Runs in | What costs time | What the report exposes |
| --- | --- | --- | --- |
| Project discovery | Rust | walking files, applying ignore rules, reading timings | path-filter errors, file counts |
| Test discovery | Rust | parsing Flow and finding declarations | `uf test --list` statuses |
| Scheduling | Rust | sorting by recorded duration or file size | warm and cold schedule counts |
| Execution | Node, Bun or Deno | importing transformed files and running cases | per-file duration, attempts, host |
| Reporting | Rust | JSON, JUnit, coverage summaries and terminal output | `run` versus `total` time |

An empty schedule is not a JavaScript problem. If a path filter, name filter or
list-only run leaves no test files to execute, uf returns before resolving or
starting a JS host. That makes mistakes cheap and makes host failures easier to
read: a missing Node binary should not be able to break `uf test --list` over
zero selected files.

When a run feels slow, first decide which number moved:

| Symptom | First thing to inspect |
| --- | --- |
| `total` is high and `run` is low | project discovery, host resolution, reporters or coverage setup |
| One worker is still busy after the rest finished | `.uf/test-timings.json` and the slowest-files table |
| A tiny suite is slower with all cores | lower `-j`; worker startup can dominate short runs |
| The selected suite is empty | `uf test --list <path> -t <name>` before running the host |
| Browser mode is slow | reduce `-j`; each worker is a browser process |

## Writing a test

```js
// @flow
import { describe, expect, it } from "@uniflowed/test";

import { total } from "./cart.js";

describe("total", () => {
  it("sums the line items", () => {
    expect(total([{ price: 300 }, { price: 120 }])).toBe(420);
  });

  it("rejects a negative price", async () => {
    await expect(total([{ price: -1 }])).rejects.toThrow("negative");
  });
});
```

Test files are Flow like everything else — `component`, `hook`, `match` and
enums all work inside one, because each worker imports its file through the same
transform a build uses.

`describe`, `it`, `test`, `beforeAll`, `beforeEach`, `afterEach` and `afterAll`
are there, with `.only`, `.skip`, `.todo` and `.each` on `it` and `describe`.
`it.skipBecause(name, reason, body?)` is the explicit skip for a case that
belongs in the suite but cannot run on this host yet. `expect` has 42 matchers,
`.not`, `.resolves`, `.rejects`, and `fn()` for spies.

Use `skipBecause` when the skipped case is a contract, not a TODO:

```js
// @flow
import { expect, it } from "@uniflowed/test";

it("runs the portable half", () => {
  expect(21 * 2).toBe(42);
});

it.skipBecause(
  "uses Node's synchronous module hook",
  "Deno runs through uf's ahead-of-time loader and import map, so this cannot exercise Node's hook.",
);
```

The reason is carried through the terminal report, `uf test --json` as
`skipReason`, and JUnit as the `<skipped message>`. That matters for ecosystem
work: a Deno or Bun run can stay green while still saying which Node-only
contract it deliberately did not execute.

## A test beside the code it tests

A three-line test for a three-line function does not always want a file of its
own. `import.meta.uf.test` is a block that lives in the module it tests, the way
`import.meta.vitest` does:

```js
// @flow
import { expect, it } from "@uniflowed/test";

export function slugify(title: string): string {
  return title.toLowerCase().replace(/[^a-z0-9]+/g, "-").replace(/^-|-$/g, "");
}

if (import.meta.uf.test) {
  it("collapses runs of punctuation", () => {
    expect(slugify("Hello,  world!")).toBe("hello-world");
  });
}
```

`uf test` finds it through the same discovery that finds a `.test.js` file —
`uf test --list` shows it, `-t` filters it, and it is scheduled and reported
like any other case. Nothing has to be configured, and there is no separate
"include" pattern: a file that declares a test is a test file.

**The block does not reach a build.** `uf` compiles `import.meta.uf.test` to
`void 0` in every transform except the ones `uf test` starts, so the bundler is
handed `if (void 0) { … }`, removes the branch, and then removes the import that
only the branch used — `@uniflowed/test` declares `sideEffects: false` so it
can. That is asserted against a real `uf build` rather than assumed: the fixture
in `crates/uf_cli/tests/fixtures/rsc-split-app` carries a string that only the
block contains, and the test reads the emitted bundle back looking for it in the
same file the module's other marker has to be present in.

The bindings come from an ordinary import, which is what makes them typed. The
marker's *value* is uf's test API, so `const { it, expect } = import.meta.uf.test`
works too and is what somebody arriving from Vitest will write — it is untyped,
because Flow has no `typeof import("…")` for a library definition to use.

Two things worth knowing:

- A source file with a block is an ordinary module, so a `.test.js` file that
  imports it for the function evaluates the block a second time. It does not
  register a second time: the marker answers with the API only for the module
  the run is currently reporting on, and with `undefined` for every other.
- Coverage counts the whole file, block included. `test.coverage.exclude`
  matches on paths, and an in-source test's path is the source file's.

## Accessibility

`expect(container).toHaveNoAxeViolations()` runs axe-core over a rendered tree:

```js
// @flow
import { expect, it } from "@uniflowed/test";
import { render } from "@uniflowed/react-testing";

import { Invoice } from "./Invoice.js";

it("is accessible", async () => {
  const { container } = render(<Invoice total={420} />);
  await expect(container).toHaveNoAxeViolations();
});
```

It is the one matcher that must be awaited — axe has no synchronous entry
point — and the published `Matchers` type says so, so forgetting the `await`
is a checker error rather than a test that passes by accident.

axe-core is an **optional dependency**: uf does not make a project that never
audits carry a megabyte of rule definitions. Add it with `uf add -D axe-core`
and the matcher starts working; write the matcher without it and you get one
sentence saying so.

The rule set is configured once, for the project:

```js
// uf.config.js
export default defineConfig({
  accessibility: {
    axe: {
      // `color-contrast` needs layout, and the DOM a Node worker renders into
      // has none — axe reports it as *incomplete* rather than as a violation.
      disabledRules: ["color-contrast"],
      minImpact: "serious",
    },
  },
});
```

An assertion may narrow further — `toHaveNoAxeViolations({ tags: ["wcag2a"] })`
— and what it passes replaces the project's answer for that one call.

**`uf dev` runs the same audit against the page on screen.** It reports through
the diagnostic channel, so a finding arrives in the terminal beside everything
else `uf dev` has to say, rather than as an overlay drawn over the markup it is
complaining about. It runs once the page settles and again after the DOM stops
changing, it is skipped while the tab is hidden, and it says nothing when
nothing changed. `accessibility.devAudit: false` turns it off; a project with no
axe-core never has it at all, and no script is injected.

This is not the same thing as `uf lint`'s `a11y/*` rules, and neither replaces
the other. The linter reads JSX that was never rendered and can see that an
`<img>` has no `alt`; the audit reads what React produced and can see that the
heading levels the component *actually* emitted skip a step.

## React Native test trees

`@uniflowed/react-native-testing` is for the half of React Native testing uf can
state honestly today: querying a native renderer's JSON tree. It can also mount
through React Test Renderer when the suite installs the optional
`react-test-renderer` peer from the same React 19.3 release line declared by
the package. That adapter is
useful for component-level checks, but it is still JSON, not a native host
config, layout engine, device, Expo app or React Navigation runtime.

When another host, app-owned harness or renderer already produced the tree,
pass that JSON directly:

```js
// @flow
import { createNativeScreen } from "@uniflowed/react-native-testing";
import { expect, it } from "@uniflowed/test";

const tree = {
  type: "ScrollView",
  props: { testID: "settings-screen" },
  children: [
    {
      type: "Pressable",
      props: {
        accessibilityLabel: "Save changes",
        accessibilityState: { busy: true, disabled: true },
        testID: "save",
      },
      children: [{ type: "Text", props: {}, children: ["Save"] }],
    },
    {
      type: "View",
      props: {
        accessibilityLabel: "Upload photo",
        accessibilityRole: "progressbar",
        accessibilityValue: { min: 0, max: 100, now: 75, text: "75 percent" },
      },
      children: [],
    },
    {
      type: "View",
      props: {
        accessibilityLabel: "Volume",
        accessibilityRole: "adjustable",
        accessibilityValue: { min: 0, max: 10, now: 6, text: "6 of 10" },
      },
      children: [],
    },
    {
      type: "TextInput",
      props: { accessibilityLabel: "Search settings", disabled: false },
      children: [],
    },
  ],
};

it("queries the native tree by role, state and value", () => {
  const screen = createNativeScreen(tree);

  const save = screen.getByRole("button", {
    name: "Save changes",
    busy: true,
    disabled: true,
  });

  expect(save.props?.testID).toBe("save");
  expect(screen.getByLabelText("Save changes").props?.testID).toBe("save");
  expect(screen.queryByRole("button", { disabled: false })).toBe(null);
  expect(screen.getByRole("textbox", { name: /Search/ }).type).toBe("TextInput");
  expect(
    screen.getByRole("progressbar", {
      name: "Upload photo",
      value: { min: 0, max: 100, now: 75, text: /percent/ },
    }).type,
  ).toBe("View");
  expect(
    screen.getByRole("adjustable", {
      name: "Volume",
      value: { now: 6, text: "6 of 10" },
    }).type,
  ).toBe("View");
  expect(screen.queryByRole("progressbar", { value: { now: 25 } })).toBe(null);
});
```

When the matching React 19.3 `react-test-renderer` peer is present, `render(ui)`
mounts the element through that JSON renderer and returns the same queries plus
`rerender`, `unmount` and `toJSON`:

```js
// @flow
import * as React from "react";
import { render } from "@uniflowed/react-native-testing";
import { expect, it } from "@uniflowed/test";

it("queries a rendered native component", () => {
  const screen = render(
    React.createElement(
      "Pressable",
      {
        accessibilityLabel: "Save changes",
        accessibilityState: { disabled: true },
        testID: "save",
      },
      React.createElement("Text", null, "Save"),
    ),
  );

  expect(
    screen.getByRole("button", {
      name: "Save changes",
      disabled: true,
    }).props?.testID,
  ).toBe("save");

  screen.rerender(React.createElement("Text", null, "Saved"));
  expect(screen.queryByText("Save")).toBe(null);
  expect(screen.getByText("Saved").type).toBe("Text");
  screen.unmount();
});
```

`render()` deliberately refuses to hide the optional peer boundary. Without
`react-test-renderer`, it raises `NativeTestingUnsupportedError` and asks the
suite to install that peer or pass an already-produced tree to
`createNativeScreen()`. Even with the peer installed, tests that need real
native behaviour should be reported as an explicit host gap:

```js
// @flow
import { it } from "@uniflowed/test";

it.skipBecause(
  "renders the settings screen on the native host",
  "uf can query React Test Renderer JSON, but this suite needs a native host config.",
);
```

The query contract is deliberately narrower than Testing Library's DOM contract,
because the input is a React Native JSON tree rather than a document:

- `createNativeScreen(root)` and `within(root)` take one root or a
  fragment-shaped array of roots. They do not mount, flush effects, compute
  layout, hide nodes or inspect native platform views.
- `getBy*` returns exactly one match and throws on zero or many. `queryBy*`
  returns `null` on zero and still throws on many. `getAllBy*` throws on zero.
- Text queries read React Native text content and avoid the duplicate
  parent-and-child match: a `Text` node whose child already matches the string
  is not reported a second time for the same visible text.
- Label queries read the accessible name directly, so
  `getByLabelText("Save changes")` finds the same node that
  `getByRole("button", { name: "Save changes" })` narrows to, and still works
  when the role is not what the test is about.
  They take only `exact`, just like text queries. A label query includes nodes
  with an explicit `accessibilityLabel` and nodes with a native role; a plain
  `View` whose name only came from a child `Text` is not reported again beside
  that child.
- Role queries use the small default map uf can defend today: `Pressable` and
  `Button` are `button`, `Switch` is `switch`, `TextInput` is `textbox`,
  `Image` is `image`, and `Text` is `text`. `accessibilityRole` or `role` wins
  over that default.
- The accessible name is `accessibilityLabel` first, then descendant text.
  Matchers may be strings, regular expressions or predicates.

`getByRole` takes the state filters React Native exposes through
`accessibilityState`: `busy`, `checked`, `disabled`, `expanded` and `selected`.
`disabled` also reads the top-level `disabled` prop, because native components
commonly put it there. A missing state reads as false, not as "unknown", so
`queryByRole("button", { disabled: false })` is the way to ask for an enabled
button.

It also takes `value` filters for `accessibilityValue`: `min`, `max`, `now` and
`text`. Those are exact numeric comparisons for the numbers and the same string,
regular expression or predicate matching for `text`, so progress bars,
steppers, sliders and other adjustable controls can be narrowed by the value a
native accessibility tree reports. A missing value field reads as `null`, which
means `value: { now: 0 }` finds a real zero and not "no value reported".

Unknown options are refused. `pressed` is not silently ignored on a native role
query, and `value: { percentage: 75 }` is refused too, because a test that asks
for a pressed button or a percentage and gets any matching role back has already
lost the thing it meant to assert. Add the state or value field to the helper
first, or assert on the returned props yourself.

That shows up as a skipped test with the reason in the terminal report,
`uf test --json` and JUnit. The JSON-level tests that can run on Node stay
green, and the native-host contract is still visible instead of being translated
into a TODO comment or a DOM-rendered substitute.

## Replacing a module

`fn()` and `uft.spyOn` replace a method on an object a test can reach. A
component that imports a client and calls it while it is being evaluated has no
such object — the import is the only seam — so `uft.mock` replaces the whole
module.

```js
// @flow
import typeof * as ClientModule from "./client.js";
import { describe, expect, it, uft } from "@uniflowed/test";

describe("the dashboard", () => {
  it("renders what the client returned", async () => {
    await uft.mock<ClientModule>("./client.js", () => ({
      send: uft.fn(() => ({ total: 420 })),
    }));

    const { summary } = await import("./dashboard.js");

    expect(summary()).toBe("420");
  });
});
```

### When a mock takes effect

**Nothing is hoisted.** Vitest lifts `vi.mock` above the importing file's
`import` declarations with a Babel pass. uf has no Babel in its pipeline and is
not adding one for a test helper, so the rule is Bun's:

- every `import` declaration runs before the first statement in the file, so a
  static import is **never** affected by a `uft.mock` written below it — it
  already holds the real module;
- a mock takes effect for every import that begins after the promise
  `uft.mock` returns settles;
- so `await import("./client.js")` is how a test reaches the stand-in.

A synchronous factory is installed before `uft.mock` returns, so the rule holds
whether or not you await. Await anyway: an automatic stand-in has to read the
real module first, and cannot be installed synchronously at all.

**A mock affects the next import, not the last one.** Nothing can rewrite a
module the host has already evaluated and linked into its importers. Bun's
engine can do that and Node's cannot, and one call meaning two things on two
hosts is worse than it meaning the narrower one on both.

**Registering or removing a mock starts a new module epoch.** A module that
imported the mocked one computed its own exports from it, so it is evaluated
again on the next import too. Modules reached by a path (`./client.js`) are;
packages are not, because a second copy of `@uniflowed/test` would be a second
registry and a second set of spies.

### The bindings

| Binding | What it does |
| --- | --- |
| `uft.mock(specifier, factory)` | Register what the module exports. The factory runs once, immediately; it may be `async` |
| `uft.mock(specifier)` | Register an automatic stand-in: functions become spies that record and return `undefined`, arrays are emptied, objects are followed, primitives are kept |
| `uft.doMock` | `uft.mock`. Vitest's two names differ only in hoisting, and uf hoists neither |
| `uft.unmock(specifier)` | Stop standing in, for imports that begin after the call |
| `uft.doUnmock` | `uft.unmock`, for the same reason |
| `uft.importActual(specifier)` | The real module, even while it is mocked — this is how a partial mock keeps the exports it did not name. It reaches past the stand-in for the module it names and for no other, so the modules *that* one imports are still mocked |
| `uft.importMock(specifier)` | The automatic stand-in, handed back rather than registered |
| `uft.resetModules()` | Evaluate path-imported modules again on the next import. It does not run a mock's factory again — register the mock again for that |

A partial mock is `importActual` and a spread:

```js
await uft.mock<ClientModule>("./client.js", async () => ({
  ...(await uft.importActual<ClientModule>("./client.js")),
  send: uft.fn(() => ({ total: 420 })),
}));
```

`uft.clearAllMocks`, `resetAllMocks` and `restoreAllMocks` reach the *spies* a
factory put in a module's exports, and none of them unmocks anything:
`clearAllMocks` forgets the calls, `resetAllMocks` forgets the implementations
too, `restoreAllMocks` puts back what `uft.spyOn` took. `uft.unmock` is the one
that puts the module back.

### The factory is type checked

`import typeof * as ClientModule from "./client.js"` names the module's shape,
and `uft.mock<ClientModule>` checks the factory against it. A stand-in whose
`BASE` is a number, for a module whose `BASE` is a string, is an error at the
call rather than a `TypeError` three tests later:

```
error[incompatible-type]: Cannot call uft.mock with function bound to factory
because in the return value: Either in property BASE: 42 [1] is incompatible
with string [2].
```

The factory is checked as a `Partial` of the module, so naming a subset of the
exports is fine and misspelling one of them is not.

### Which hosts

Node only. Interception needs synchronous, in-thread module customization hooks
— `node:module`'s `registerHooks` — because a mock is a value the test built and
a loader running on a thread of its own cannot see it. Bun's `node:module` has
no such hook, and Deno runs a suite that uf compiled before the host started
rather than through a hook it could intercept
([#246](https://github.com/ubugeeei-prod/uf/issues/246)), so on either host all
seven bindings raise `UnsupportedError` naming the host, the hook and what to do
instead. None of them silently does nothing, and on Bun that is checked by
starting a real Bun and asking.

Bun's plugin API is not a second route to this, which is worth saying because it
looks like one:
[#419](https://github.com/ubugeeei-prod/uf/issues/419) has what a Bun 1.1
`onResolve` does with each of the three places a stand-in could be given an
identity of its own, and none of them survives an `import` declaration — which
is the case the feature exists for. Bun's own `mock.module` survives one, and it
maintains live bindings: it changes a module somebody has already imported,
which is a different promise from the one above rather than the same one on a
second host.

The summary is meant to be read after the run, not decoded:

`run` is the suite itself. `total` includes the surrounding work: reading the
project, resolving the host, loading timings, writing reporters, and drawing the
report. A gap between the two says "the tests were not the slow part". The
`schedule` row tells you whether this was a warm schedule from recorded
durations or a cold one from file size, and `host` names where the test bodies
actually ran.

### What runs where

`uf test` keeps orchestration in Rust and execution in JavaScript:

1. Rust reads the project and scans Flow source for declarations without
   importing the modules.
2. It applies path filters, `-t`, `.only`, `.skip` and `.todo`, then sorts files
   longest-expected-first.
3. It starts at most one worker per core, or the number from `-j`. Once a run
   has recorded durations, it starts only as many workers as the suite can keep
   busy for longer than one takes to boot — see
   [Timings and scheduling](#timings-and-scheduling).
4. Each worker imports a file through the same `uf transform` path the build
   uses, runs the declarations, and streams structured events back.
5. Rust owns retries, bail, file timeouts, the report, JUnit, JSON and coverage
   threshold failures.

That split is why a syntax or transform bug fails in the same place in tests and
builds, while scheduling and reporting stay deterministic enough to compare in
CI. A worker may serve more than one file, but every file starts from the same
test state: spies are cleared, fake timers are restored, module stand-ins are
dropped, and `stubEnv` / `stubGlobal` writes are put back.

### Keeping the loop fast

The fast local loop is usually three commands:

```console
$ uf test --list
$ uf test app/cart -t "discount"
$ uf test --watch app/cart
```

`--list` is not a dry run of the worker; it is the discovery view. It tells you
which declarations are runnable, skipped, filtered, unsupported, or from
another runner before a host is started. That is the cheap way to catch a bad
path, a misspelled filter, or a `node:test` import that would otherwise look
like "nothing ran".

Path arguments are substring filters over files, and `-t` is a substring filter
over the fully qualified name, including `describe` parents. Named paths
override `.gitignore` on purpose, so an ignored fixture directory can still be
tested by name; a path that matches no project file is refused, because a green
run over a typo is worse than a red one.

`--watch` re-runs what the changed file invalidated. It is for answering "did
my edit break the nearby tests?", not for whole-project proof, so it cannot be
combined with `--json` or `--coverage`: both promise a single report about one
complete suite.

### Timings and scheduling

After a run, uf records completed file durations in
`.uf/test-timings.json`. The next run uses those numbers to put expensive files
first, because the slowest worker decides when a parallel suite finishes. A new
file, or a run with no timings yet, falls back to source size. The summary says
how many files were scheduled from each source.

The same file records what one worker cost to start, and the next run uses it to
decide **how many** workers to start, not only in what order to feed them. A
worker is a process that has to boot and load the test API before it runs a
line, so a suite of two-millisecond files is finished by two workers before a
third has booted — and on a laptop whose cores are half efficiency cores, the
extra workers take cores away from the ones doing the work. uf adds workers one
at a time while the next one would shorten the run by more than it costs to
start, so a short suite gets two or three and a suite with seconds of work gets
every core. A cold run, with nothing recorded, starts one per core as it always
has; `-j` is always taken exactly as written. The summary's `workers` row is
the number that ran.

A file's recorded duration is the file's own. The first file a worker is given
used to be charged for the worker booting, which made one file per worker look
tens of milliseconds slower than it was, in the slowest-files table and in the
numbers the next run scheduled from.

The timings file is a cache, not an input you have to curate. If it is missing,
corrupt, too large, or contains a path or duration uf will not believe, the run
schedules cold and says so. It is rewritten with only files still in the
project, and failure to write it is a note rather than a failed test run.

`-j` is still worth typing when you know something the recorded durations do
not:

```console
$ uf test -j 1      # serial, easiest to debug ordering-sensitive failures
$ uf test -j 8      # every core, whatever the last run recorded
$ uf test --browser -j 2
```

Browser workers are full browser processes with scratch profiles, so `-j 2` may
be the right CI value even on an eight-core runner. The terminal summary tells
you how many workers actually ran and which files dominated the wall clock.

### Host choice and skips

The host is the first of these that says something: `test.runtime`, the
runtime `test.runner` brings, then `runtime`. `test: { runtime: "bun@1.4" }`
runs the suite on the Bun 1.4 release `uf.lock` locks, installed into the store
the first time a run needs it — see [Environments](/guide/env). With none of
them, the host is the project's Capability JS Host:
`app.runtime.capabilityJsHost.default`, with auto-detection if the project kept
that on. `uf explain test` names the host, the key that chose it and the
release it is locked at, and is the fuller answer when a permission, loader or
runtime question is involved.

A missing host, a host without the requested capability, or a feature that would
be silently partial is a command refusal. A test case that belongs in the suite
but cannot run on the current host is a skip:

```js
it.skipBecause(
  "collects coverage on Bun",
  "coverage is V8 data written by Node today; keep the Bun contract visible until the host can provide it.",
);
```

That distinction is the useful one in ecosystem work. Refusals say "this run
would lie"; `skipBecause` says "this known contract is still absent here", and
the reason survives in the terminal report, `--json` and JUnit.

### Reports for CI

CI usually wants two outputs:

```console
$ uf test --json > test-results.json
$ uf test --reporter junit --reporter-outfile junit.xml
```

`--json` is uf's full document. It includes the resolved host, whether that host
loads Flow and collects coverage, warm/cold scheduling counts, file statuses,
case statuses, attempts, durations, captured output and unsupported
declarations. Durations live in `durationMicros` fields so a program can ignore
only those when comparing two runs.

JUnit is intentionally narrower: one `testsuite` per file, one `testcase` per
declaration, failures as `<failure>`, import/time-out/host failures as
`<error>`, and skips with the skip reason as the `<skipped message>`. Use it
for pull request annotations and CI test tabs; use `--json` when a job needs to
make a policy decision.

For coverage in CI, keep the project policy in `uf.config.js` and let the
command only choose whether to measure:

```console
$ uf test --coverage --coverage-reporter lcov --coverage-reporter cobertura
```

Threshold misses fail with the same non-zero exit as a failing test. LCOV and
Cobertura are files for other services; the JSON report grows a `coverage`
object only when coverage was actually collected.

## Browser mode

<div className="command"><code>uf test --browser</code></div>

`@uniflowed/react-testing` renders into happy-dom, which is fast, runs anywhere,
and **computes no layout at all**. That is fine until a component's behaviour
depends on its size, and then it is not fine in a particular way:

| Asked of a half-width box | happy-dom | a browser |
| --- | --- | --- |
| `getComputedStyle(el).width` | `"50%"` | `"300px"` |
| `el.getBoundingClientRect().width` | `0` | `300` |
| `el.offsetWidth` | `0` | `300` |
| an `IntersectionObserver` on it | never fires | fires |

The first row is the expensive one. happy-dom does not decline to answer — it
resolves the cascade and hands back the *declared* value under the name of the
computed one. A test asserting that a panel is half its container's width passes
against a string that says nothing about width, and keeps passing after the
component stops being half its container's width.

`--browser` runs the same files, with the same `describe` / `it` / `expect`, in
a page. `tests/library/browser-layout.test.js` in this repository is the table
above written as assertions, and it runs in both modes.

### What it is

**A host, not a second runner.** Node and Bun are hosts `uf test` fans files out
to; the browser is a third. `uf` still discovers the files, orders them
longest-first from recorded timings, decides how many run at once, bounds each
one with a wall clock it will not negotiate, retries what the retry policy says
to retry, and assembles the report. None of that knows a browser is involved.

What it starts is a small Node process that serves the page its modules —
transformed by the same `uf transform` a build uses — and shuttles JSON between
a pipe and a socket. A page cannot read a pipe; that is the whole reason there
is a process in the middle.

**One page load per file.** This is stronger isolation than Node mode gets. A
Node worker serves many files out of one process, so everything two files could
share has to be put back between them by hand. A page reloads: new realm, new
document, new module registry, and a `setInterval` the last file abandoned is
gone rather than merely ignored.

**One browser per worker.** `-j` means what it always meant — how many files run
at once — and in browser mode each of those is a browser process with a scratch
profile of its own. That is a few hundred megabytes each, so `-j 2` is worth
typing on a small CI container; nothing about the flag changes, but what it
costs does.

**Not every test file belongs here.** `--browser` runs the files it is given,
and a file that imports `node:fs`, spawns a process or reads a fixture off disk
cannot run in a page — the import is refused by name, and the file is reported
as failing to load. That is the right answer rather than a bug: point
`--browser` at the component tests, which is the half of a suite it is for.

### What it depends on

**A browser you already have.** uf does not download one, does not vendor one,
and does not pin a version. It looks on `PATH` for `chromium`, `chrome`,
`google-chrome`, `google-chrome-stable`, `microsoft-edge` and `brave-browser`,
then for an installed Google Chrome, Chromium or Microsoft Edge; `UF_BROWSER`
names one outright and is never second-guessed.

With none of those, the run is **refused**, and the message lists everything it
looked for. It does not fall back to the shim: you asked for a browser because
you stopped believing the shim's answer, and a green run on it would be an
answer to a question nobody asked.

The list is Chromium-shaped and the reason is not favouritism. A run needs to
tell a browser from a command line to open a page headlessly, keep it open, and
take a scratch profile. Firefox and Safari each need a driver protocol for that,
and adopting one would make the test runner own a browser automation library.

There is no Playwright here and no Puppeteer. The browser is started with a URL
and left alone; everything uf learns comes back over HTTP from the page's own
code.

One switch is worth naming because it looks like an exception and is not.
`--remote-debugging-pipe` is passed, and uf never writes a byte to it: Chrome
treats that pipe as its lifeline and shuts down when it closes. That is what
makes the browser die with the process that started it — `uf` kills a worker
that misses its deadline, a killed process runs no exit handler, and without the
pipe a timed-out file would leave a browser running with nobody to stop it. A
pipe rather than `--remote-debugging-port` because a port is something anything
on the machine can speak to.

### What it cannot do yet

That last paragraph is a ceiling as well as a floor. **uf cannot drive this
browser.** No clicking a real cursor, no navigation, no screenshots, no network
throttling, no second tab. Those are the other half of
[Playwright-compatible browser automation](https://github.com/ubugeeei-prod/uf/issues/517)
and they want the protocol this mode deliberately does not speak. `fireEvent`
and `userEvent` work exactly as they do on Node, because they dispatch DOM
events — which is a different thing from driving a browser, and enough for a
component test.

Four more, each refused by name rather than half-done:

- **Snapshots.** `toMatchSnapshot` writes a file beside the test that took it,
  and a page has no filesystem. `uf test --browser -u` is refused; record
  snapshots on Node and check them in the browser.
  `toMatchInlineSnapshot` needs no file and works.
- **Module mocking.** `uft.mock` intercepts module resolution, which is
  `node:module`'s synchronous hooks on Node and nothing at all in a page.
- **Coverage.** V8 is counting in the renderer exactly as it counts in Node, but
  `NODE_V8_COVERAGE` is Node's own switch and the only way to ask a page for its
  profile is the protocol above. `--browser --coverage` is refused before the
  browser is even looked for, because installing one would not fix it.
- **`permissions`.** A declared set describes what a *process* may reach, and
  the process the tests run in is a browser uf started rather than a host uf
  configured. Sandboxing the driver instead would produce a run that reads as
  sandboxed and a renderer with the whole machine's network, so the run is
  refused instead.

Anything a page cannot have — `node:fs`, a synchronous `require` — throws a
sentence naming what is missing and what to do instead, at the moment it is
reached. None of them answers plausibly and moves on.

## Coverage

`uf test --coverage` reports coverage **against the Flow you wrote**, not
against the JavaScript uf printed for it.

```
coverage
file                    lines      functions      branches  uncovered
src/badge.js  85.71% (12/14)  66.67% (2/3)   50.00% (1/2)  17-18

lines      85.71% (12/14)
functions  66.67% (2/3)
branches   50.00% (1/2)
wrote coverage/lcov.info
```

Nothing is instrumented. V8 counts execution on its own, Node writes those
counts out when a worker exits, and uf maps them back through the same source
map the transform already produces. So the code the suite ran is the code you
shipped, byte for byte — which is not true of any tool that rewrites your source
to count it.

### What the three numbers mean

Every tool means something slightly different by "branch", so here is uf's, in
full. One rule decides all three: **a position in the output that maps to
nothing you wrote is not counted at all.**

| Metric | Counted | Covered |
| --- | --- | --- |
| Lines | An author line that at least one generated position maps back to | The innermost V8 range over one of those positions ran at least once |
| Functions | A generated function whose body holds at least one mapped position, attributed to the first one | It was entered |
| Branches | A V8 *block* — an `if` or ternary arm, a `&&` right operand, a loop body, a `catch` — whose first mapped position exists | It was entered |

The rule is what keeps the compiler out of your numbers. A `type` alias
generates nothing, so it is not a missed line. A `match` lowers to a chain of
tests you did not write, and those tests are not branches you failed to cover.
The enum runtime and the React Compiler's memo blocks are not functions you
forgot to test. None of them is reported as covered either — they are simply not
in the denominator, because they are not your program.

A file the suite never loaded is named rather than scored: it has no measured
line to divide by, and `0/0` — which every other ratio here calls a hundred per
cent — would make a file nobody imports the best-covered file in the project.

### Failing a build on it

Thresholds live in `uf.config.js`, not on the command line, because the number
CI fails on has to be the number a laptop fails on.

```js
export default defineConfig({
  test: {
    coverage: {
      reporters: ["text", "lcov"],
      thresholds: { lines: 80, branches: 70 },
      perFileThresholds: { lines: 50 },
    },
  },
});
```

They are checked whenever coverage was collected, however it was asked for, and
a threshold that is not reached fails the run with a non-zero exit code and a
line per miss. A metric nobody names is not checked.

### The files CI reads

| Reporter | File | Who reads it |
| --- | --- | --- |
| `text` | — | The terminal table above |
| `lcov` | `coverage/lcov.info` | Codecov, Coveralls, `genhtml`, the GitHub and GitLab coverage widgets |
| `cobertura` | `coverage/cobertura-coverage.xml` | Azure Pipelines, Jenkins |

`--reporter junit --reporter-outfile junit.xml` writes the *results* — one
`testsuite` per file, one `testcase` per declaration — which is what turns a
failing test into an annotation on a pull request. It needs an outfile because
`uf test --json` already owns stdout for a machine.

`uf test --json` grows a `coverage` object when a run measured, and it is absent
rather than empty when it did not: a check reading the document has to be able
to tell "not measured" from "measured, and bad".

### What it does not do yet

Coverage is **Node only**. It is V8's own count, written through
`NODE_V8_COVERAGE` and mapped through the source map Node's loader attached;
Bun implements neither, and Deno, which runs a suite uf compiled ahead of time,
has no such switch either. `uf test --coverage` on either says so rather than
reporting zeroes.

`--watch` and `--coverage` cannot be combined: watch mode re-runs the files an
edit affected, so its coverage would be a number about three files wearing the
project's name.

## What it gets right

**A file that throws while importing is a file failure, not "0 tests".**
Reporting a module that could not load as having no failing tests would be a
lie.

**A file that registers nothing is a file failure too.** `uf test` reads
`describe`, `it` and `test` out of your source to decide what to schedule, and
the worker reports what those calls actually registered. When the first number
is positive and the second is zero, none of the file ran — the bindings were
another runner's, or the file's own, or the registrations were inside a branch
this run did not take — and the run says so instead of counting the file as
done. A file that deliberately runs nothing writes `it.skip`, which registers
and is reported as a skip.

**Another runner's `test` is not a test uf can run, and saying so is the
run's job.** `test("...")` is the same eight characters whoever exports the
binding, so `uf test` reads the import it came from. A name bound by
`node:test`, `vitest`, `jest` or their peers is listed under *unsupported
declarations*, is not counted as runnable by `--list`, and makes the run
non-zero — `node:test` especially, because it accepts the registration and
keeps it for a runner that is never started, so the file loads, reports
nothing, and would otherwise pass. Only a runner that can be named is treated
as one: `import { it } from "../support/setup.js"` re-exporting uf's own `it`
is an ordinary thing to write and runs as it always did.

`it.each(...)` is listed there too and does *not* fail the run. It is uf's own
`it` in a form discovery cannot expand, so `--list` cannot name the cases ahead
of time — but the worker runs them and the report counts them, which is the
whole difference.

**A test that never settles is failed, not hung.** The worker races each case
against its budget, and Rust keeps its own wall-clock deadline and kills the
process — because a wedged event loop would never have run the worker's timer
either.

**A retry re-runs the file**, filtered to one case. A case cannot be re-entered
without re-importing its module, and a retry has to see the module state a first
run would.

**`.only` is decided after the module body runs**, since a file's `.only` can
appear below the tests it excludes.

**One worker serves many files, and each one starts from the same place.**
Between files the worker clears the registry, puts every `stubEnv` and
`stubGlobal` back, restores the real clock, and drops the module stand-ins a
`mock` installed. When a file rendered, the window goes back too: the
properties a test assigned on it (a removed `matchMedia` is the usual one), the
attributes on `<html>` and `<head>`, and the globals a render installed — so a
file that never renders gets Node's own `FormData` and no `document` at all,
exactly as in a fresh worker, and the next render puts the same window back.
The URL is not reset, because the router keeps its own state in step with it;
a test that depends on the address sets the one it needs. An axe
audit a timed-out case abandoned is waited for rather than failing the next
file's. Spies and mocks live in state the runner owns; a stub and a
fake clock are writes to something the whole process shares, so without this a
file that called `uft.useFakeTimers()` and forgot to restore it would leave the
*next* file's `setTimeout` never firing — a hang, with nothing on screen,
blamed on the file that waited rather than the file that stopped time. Which
files follow which changes with the timings cache, so a suite that depended on
it would fail differently every run.

## Choosing a runner

`uf test` runs a suite with uf's own runner unless `uf.config.js` names another:

```js
export default defineConfig({
  test: { runner: "bun" }, // or "bun@1.4", which `uf env install` installs
});
```

With `runner: "bun"`, uf still discovers the test files — the same files its own
runner would run — and hands exactly those to `bun test`, with uf's Flow preload
loaded, so a test file written in Flow imports. The test files do not change:
they keep importing `@uniflowed/test`, and uf starts Bun with an export
condition under which that package *is* `bun:test`. `uf explain test` prints the
exact command.

**What maps.** `describe`, `it` and `test` with `.only`, `.skip`, `.todo` and
`.each` (rows are handed to the body whole, as uf's own runner does), the four
hooks, `fn`, `spyOn`, and `uft`'s clock and mock-reset members are Bun's.
`expect` is Bun's too, so its own matchers work — and its failure messages are
Bun's.

**What refuses.** Anything with no Bun equivalent raises `UnsupportedError` at
the moment it is used, naming what was called: `it.skipBecause` (Bun's skips
carry no reason into a report), the DOM matchers and `toHaveNoAxeViolations`,
the snapshot matchers (the two runners key snapshots differently, so a snapshot
would be compared against, or rewritten over, one uf did not write),
`uft.stubEnv` and `uft.stubGlobal`, module mocking, and
`uft.advanceTimersByTimeAsync`. `uf test` itself refuses, before Bun starts, a
project that declares `permissions` or coverage thresholds, and in-source tests
— each is a promise uf keeps for its own runner and cannot keep through Bun.

**Flags.** Path filters, `-t` (still a substring: uf escapes it for Bun's
regular expression), `--watch`, `--bail`, `--retry`, `-j`, `--coverage` with
`text` or `lcov`, and `--reporter junit --reporter-outfile` mean the same thing
to Bun and pass through. `--json`, `--list`, `--browser`, `--watch-interval`,
`-u` and a Cobertura report do not, and are refused by name rather than dropped.
Coverage under Bun is Bun's own count of the JavaScript the preload produced,
not uf's mapping back to your Flow lines.

**What uf still checks.** Bun reports a file whose registrations went somewhere
it could not see as "0 tests" and exits 0. So uf always has Bun write a JUnit
report, reads it back, and fails the run when a file its discovery says declares
tests produced no case at all — the rule uf's own runner enforces for the same
reason.

**The difference, measured.** Relative numbers, and only relative: they were
taken on a shared 8-core M3 under a load average of 20–23 from other builds,
with the runners alternating in the same minutes over 15 rounds, so every time
below is inflated and only the ratios carry over. Absolute numbers on a quiet
machine belong to the benchmark in
[#945](https://github.com/ubugeeei-prod/uf/issues/945). The suite is 50 Flow
files and 1,000 cases:

| Run | Wall, median (p25–p75) | CPU |
| --- | --- | --- |
| `uf test`, `runner: "uf"`, warm cache | 432 ms (399–442) | 410 ms |
| `uf test`, `runner: "bun"` | 766 ms (711–817) | 230 ms |
| the `bun test` command that starts, alone | 757 ms (670–802) | 220 ms |
| `bun test` on the same suite as plain JavaScript | 286 ms (264–361) | 110 ms |

What `uf test` adds around `bun test` is within the noise, 766 against 757 ms.
A Bun runner takes longer than uf's own here for one reason: Bun's preload
compiles every Flow module through `uf transform` on every run, where uf's
runner reads them back from `.uf/cache/transform`. That compile is also most of
the gap to plain `bun test`, and caching it is the next change in
[#944](https://github.com/ubugeeei-prod/uf/issues/944). It already uses about
half the CPU of uf's runner.

Keep the default for what only uf's runner does — module mocking, DOM matchers
and accessibility audits, coverage against your Flow source, permissions,
browser mode, and skip reasons that survive into reports. Choose Bun for a suite
that already relies on Bun's own matchers or behaviour.

## Where it stands

50 files, 1,000 tests, 2,000 assertions, on an 8-core M-series Mac, best of
five, each runner on its own idiomatic input:

| Runner | Time |
| --- | --- |
| `bun test` | 0.06 s |
| `uf test`, warm transform cache | 0.20 s |
| `uf test`, cold | 0.30 s |
| `vitest run` | 1.96 s |

About nine times faster than Vitest. About **three times slower than Bun**,
which is the bar uf is aiming at and does not clear yet.

The gap is process start-up and inter-process messaging. Bun runs everything in
one process with the runner built into the engine; uf spawns a worker per core
and each one loads the test API before it can do anything. That is also why
`-j 4` beats `-j 8` on this suite — past a point, another worker costs more to
start than the work it takes. Closing the gap needs a worker pool that survives
between runs and a pre-bundled worker. Neither exists yet.

## Not there yet

- No concurrent cases within a single file, and no `--shard` for splitting a
  suite across machines.
- Coverage is Node-only, and a worker that has to be killed — a file that timed
  out, a worker that crashed — takes its counts with it, because they are
  written when the process exits.
- Module mocking is Node-only; see "Which hosts" above.
- The accessibility audit is only as good as the DOM under it. On a Node worker
  that is happy-dom, which computes no layout, so `color-contrast` and the rules
  about overlapping targets come back *incomplete* rather than decided. `uf dev`'s
  audit runs in a real browser and answers them.
- `@uniflowed/react-testing` needs a DOM and says so when called; component
  tests need one supplied.
- Deno runs a suite through an ahead-of-time pass rather than a loader, so a
  module the pass could not enumerate — a path computed at run time, a file a
  test writes and then imports — is still Flow when Deno meets it, and
  `uf test --watch` is refused there.
